# UI review 2: keyboard-config after the rework (2026-11-16)

Reviewer: app-designer, REVIEW mode. This is a fresh, critical pass. It is not graded on a curve for following the brief, and where the brief itself was wrong, this report says so.

## Verdict: REWORK

The rework is a real step up from the original: tokens, the shared shell, labels, the swap-aware board, inline confirm, and copy are mostly right. It still does not ship, for four reasons:

1. **Lighting has a dead-end state.** If the keyboard is plugged in but the app has no permission, the page stays on "Reading…" forever and shows no error.
2. **Remap at 1280×800 fails its own focal-point goal.** The bottom row of the board sits under the sticky apply bar.
3. **Remap and VIA scroll sideways at 360px.** The earlier report said "verified no sideways scroll". That is no longer true.
4. **Three interaction bugs** break keyboard users and mouse or touch users: focus is lost after every async action, slider dragging is broken, and the banner is re-announced on every render.

## Method

- I read every file named in the task.
- I ran the built UI in headless Chromium through the Vite dev server. The `/api/*` responses were mocked for each state: ok, server down, Hyprland down, keyboard absent (`present:false`), and no hidraw permission (HTTP 503 `EACCES`).
- Viewports were 1280×800, 768×1024 and 360×740, each in light and dark.
- The measurements below come from `getBoundingClientRect` and `scrollWidth` in that browser, not from estimates.
- Not run: axe, a screen reader, or real hardware.

## P0: blocks ship

### P0-1. Lighting: "no permission" and "keyboard not replying" leave the page stuck on "Reading…"
- **Where:** `src/rgb/main.ts:93-104`, `:269-287` and `:304-307`; `server/rgb.ts:48-50`; `server/hidraw.ts:40`.
- **Evidence:**
  - `openSync` throws `EACCES` on a hidraw node the user can't open. The server turns that into HTTP 503 `cannot open the keyboard: EACCES…`. It never returns `present:false`.
  - The client's `load` catches the error and calls `say()`. But `ui.server` is still `null`, so `draw()` renders the loading skeleton, which has **no apply bar**. The result line that would show the error is therefore never on screen.
  - `banner()` only handles `present:false`.
  - Measured: the chip stays on `Reading…`, there is no banner, and the error appears only in the hidden `#live-alert`. The skeleton reads `Static · #000000 · Off`, and the disabled controls look like a keyboard that is off.
  - This is the most likely first-run failure, since the udev rule has not been installed yet. The brief is partly to blame: section 6.7 assumed "no permission" arrives as `present:false`.
- **Fix:**
  - Track `ui.loadError` and map it in `banner()`.
  - A 503 whose message contains `EACCES` or `EPERM` gets the bad-tone banner **"The app can't open the Rover 84"**. Body: `It's plugged in, but this app doesn't have permission. Install the udev rule once (README, Lighting section), then unplug and replug the keyboard.` Details: the raw message. Action: [Try again].
  - Any other load failure gets **"Couldn't read the keyboard"** with the raw message in details and [Try again].
  - Set the chip to `Keyboard not found` (bad) in both cases.
  - Hide the skeleton when a load has failed. Show it only while a first load is actually in flight.

### P0-2. Remap at 1280×800: the bottom row of the board is under the apply bar
- **Where:** `src/remap/main.ts:395`; `src/style.css:151`, `:345-348`, `:355-356` and `:359-366`.
- **Evidence:**
  - The settings card spans 126 to 359px (233px tall). The board spans 472 to 743px. The sticky apply bar starts at 730px. So the last 13px of the bottom row (Ctrl, Super, Alt, Space, arrows) are hidden, and the legend and caption are fully below the fold.
  - With any banner showing, everything moves down another 135px (Hyprland-down screenshot).
  - The board unit is 45px, not the "about 50px" the brief predicted.
  - The sticky inspector's `max-height: calc(100vh - 32px)` also ignores the 70px bar, so the bottom of the picker scrolls under the bar.
- **Fix:** do (a) and (b) together; (c) is an alternative for (a).
  - **(a) Compact settings strip at ≥1024px, about 96px tall.**
    - Visually hide the card's h2 (keep it for screen readers).
    - Device field on one row: label, then the 24rem input, then the `Found: Rover 84 V3 (2 inputs)` helper inline after it.
    - Swap switch on the right, with a one-line helper: `For Mac mode. Stays on after Turn off remap.`
    - Move the long explanation into a `<details>` called `Why?`.
  - **(b) Make the h1 `.sr-only` at ≥1200px.** It repeats the active nav item directly above it and costs 54px. Add `--bar-h: 72px` and use `max-height: calc(100vh - var(--bar-h) - 2 * var(--s4))` on `.inspector`.
  - **(c) Alternative to (a):** at ≥1200px use `grid-template-areas: "board inspector" "settings inspector"`, so the board is the first thing under the header.
  - **Target:** the board's bottom edge at or above 620px with no banner, so the legend also clears the bar.

### P0-3. Remap and VIA scroll sideways at 360px
- **Where:** `src/style.css:262` (`.tabs` uses `grid-template-columns: repeat(4, 1fr)`) and `:157-160` (`.card` is a grid with an implicit `auto` column).
- **Evidence:**
  - Measured `scrollWidth` is 367 against `innerWidth` 360 on `/` and on `/via.html` once connected.
  - The elements overflowing are the inspector h2, the helper text, Reset, search and the tabs, all reaching x=367.
  - Cause: `1fr` has an `auto` minimum, so the "Punctuation" and "Navigation" labels force each column to about 85px. The card's implicit column then grows to that min-content width.
  - The screenshot shows the inspector content running past the card's right edge.
- **Fix:**
  - `.card { grid-template-columns: minmax(0, 1fr); }`
  - `.tabs` at ≤767px: `grid-template-columns: repeat(4, minmax(0, 1fr))`, and on the tab buttons `font-size: var(--fs-12); white-space: normal; line-height: 1.15`.
  - Or use 2 columns below 400px.
  - Re-run the checklist test `document.documentElement.scrollWidth <= innerWidth`.

## P1: must fix in this rework

### P1-1. Focus drops to `<body>` after every async action (Apply, Write, Turn off, Re-read, Restore)
- **Where:** `src/ui/focus.ts:12-24`, `src/remap/main.ts:348` and `:351`, `src/rgb/main.ts:313` and `:323`.
- **Evidence:**
  - The busy render disables the button that was clicked. `focus()` on a disabled element does nothing, so focus falls to `<body>`.
  - The next render then has no `data-fid` to restore.
  - Measured: after Apply on Remap, `activeElement` is BODY. After Apply on Lighting it is also BODY, and it is already BODY during the busy state.
  - This fails the brief's own checklist item "click, then Tab moves to the next control". Picker clicks are fine (focus stays on `pick-KeyB`).
- **Fix:**
  - In `focus.ts`, keep `lastFid` at module level and fall back to it when `activeElement === body`.
  - Better: while busy, use `aria-disabled="true"` plus a click guard instead of `disabled`, so the button keeps focus. Keep `disabled` only for states that are really unavailable.

### P1-2. Dragging the Brightness or Speed slider moves it only one step
- **Where:** `src/rgb/main.ts:135`, `:188` and `:197`.
- **Evidence:**
  - Each `input` event calls `render()`, which replaces the `<input type=range>` in the middle of a drag, so the pointer loses the element.
  - Measured: press at the left end, drag smoothly to the right end, release. The value ends at `0`; it should be `4`.
  - Touch has the same problem. Arrow keys still work because focus is restored.
  - The native colour input (`:164`) probably has the same issue; check it in a browser.
- **Fix:**
  - On `input`, update only the value label, `aria-valuetext` and the preview plate's `--glow`/`--led` variables, without a full re-render.
  - Call `render()` on `change`.
  - Do the same for the colour picker (`input` → preview only, `change` → render).

### P1-3. Every disabled swatch, switch and slider turns into a grey slab, and Lighting flashes on every write and every window focus
- **Where:** `src/style.css:191-193` (`button:disabled` beats `.swatch`/`.switch` on specificity), `:253`; `src/rgb/main.ts:323` and `:336-338`.
- **Evidence:**
  - Measured background on a disabled `.swatch` and `.switch`: `rgb(233,236,240)`.
  - In the screenshot each colour dot sits in a grey 44px square, and the switch's track loses its border, leaving only a grey thumb floating in a grey box.
  - All controls are disabled during `busy`, and `busy` is set by the automatic re-read on **every window focus**. So the whole Backlight panel flashes grey every time the user alt-tabs back.
- **Fix:**
  - Scope the disabled rule: `.swatch:disabled, .switch:disabled, .key:disabled { background: transparent; }`, and give `.switch:disabled .track` a `--control` border at 50% instead of `transparent`.
  - Do not disable controls during a quiet re-read: pass `disabled` only for `Writing…` and `Restoring…`.

### P1-4. The banner is re-created on every render, so screen readers repeat it
- **Where:** `src/ui/shell.ts:56-58` and `:88-89`, plus every `draw()`.
- **Evidence:**
  - `replaceChildren` rebuilds the banner each time with `role="alert"` (server down) or `role="status"`.
  - A newly inserted live region that already has content gets announced, so every keystroke in search and every click re-reads "Can't reach the local server…".
  - Not checked with a screen reader, but this is well-known behaviour.
- **Fix:** render `.banner-slot` once, outside `#app` (the same pattern as `#live-status`), and replace its content only when the banner's title or body changes.

### P1-5. `<details>` lost its disclosure marker, so "Show input names" and "Technical details" look like plain text
- **Where:** `src/style.css:217` and `:385` (`summary { display: flex }` removes the `list-item` marker).
- **Evidence:** in the screenshots, "Show input names" and "Technical details" sit below the helper text in the same weight, with no affordance.
- **Fix:**
  - `summary { display: list-item; }`, or add a CSS chevron: `summary::before { content: ""; border: solid currentColor; border-width: 0 2px 2px 0; padding: 3px; transform: rotate(-45deg); margin-right: var(--s2); }`, rotated 45deg when `[open]`.
  - Colour: `--accent` with an underline on hover.

### P1-6. Remapped keys can't be told apart from default keys by luminance
- **Where:** `src/style.css:314`; tokens `--accent-tint` against `--cap`.
- **Evidence:**
  - The contrast between `--accent-tint` and `--cap` is **1.19:1** in light and **1.06:1** in dark. In dark the "highlighted" cap is actually *darker* than a normal one (L 0.025 vs 0.021).
  - The only other cue is the legend text, which means reading every key. That fails WCAG 1.4.11 for a state indicator, and it fails the brief's "single accent keycap" idea: the remapped key should pop.
- **Fix:**
  - Add a non-fill cue: `.key.mapped .cap { border-color: var(--accent); border-bottom-color: var(--accent); }`. Accent on cap is 6.54:1 light and 6.23:1 dark.
  - Keep the 2px all-sides accent border for *selected* so the two states stay distinct. Mapped gets 1px, selected gets 2px plus an inset ring.

### P1-7. Banner and apply bar are 64px wider than the content column
- **Where:** `src/style.css:208`, `:211`, `:364` and `:366` compared with `:151-152`.
- **Evidence:** at 1280px the cards span x=72 to 1208, but the banner and bar span x=40 to 1240. `100% - 2*s6` is measured from the viewport, while the shell's 1200px max-width already includes its own padding. Edges that don't line up make the page look sloppy.
- **Fix:** `width: min(calc(100% - 2 * var(--s4)), calc(1200px - 2 * var(--s4)))` below 1024px, and the `--s6` equivalent at 1024px and up. Or wrap the banner and bar in a container that uses the shell's exact padding.

### P1-8. Swap switch: the label and its helper are about 60px apart
- **Where:** `src/style.css:237` and `:355-356`.
- **Evidence:** `.settings-grid` stretches the swap column to the height of the device column (142px). `.switch-row`'s two auto rows share the extra space, so the helper drifts away from its label (see the 1280 screenshot). This is exactly the "uneven gaps" mess the brief was written to remove.
- **Fix:** `.switch-row { align-content: start; }` (or `.settings-grid { align-items: start; }`).

## Where the build drifts from the brief

These are deviations in the implementation, and a few places where the brief itself was wrong:

- 5.1 / checklist: "board and picker visible at 1280×800". **Fails** (P0-2). The brief's 50px board unit was optimistic; the real value is 45px.
- 4.3: "tabs never wrap unevenly". **Fails** in the desktop inspector (P2-2) and overflows at 360px (P0-3).
- 4.10: board card padding below 1024px was not implemented (P2-1).
- 2.2: "nothing smaller than 12px". The 10px `small` violates it (P2-7).
- 5.3: the "no keyboard matched" row is implemented only when N > 0 (P2-15).
- 5.7: `Reset this key` is shown in every state (P2-4).
- 6.7: **brief error.** "No permission" is not `present:false`; it arrives as a 503 (P0-1).
- 4 (disabled rule): **brief error.** A global "disabled = sunken background" breaks the custom controls (P1-3). The rule should be scoped to text controls.
- Added copy that is not in the brief: `Ready.`, and `Server offline` (the second one is fine; keep it).

## What is good (keep)

- One cobalt accent, used with restraint: primary, focus, switch-on, selection, links. Semantic colours are separate and always come with words.
- No gradients, glows or emoji.
- Real `<label for>` on every input, and `aria-current` in the nav.
- The skip link and persistent live regions.
- Inline confirm that focuses Cancel, closes on Esc and returns focus to the trigger.
- The swap-aware board, with correct codes and `aria-label`s.
- The friendly device name, with raw names behind details.
- The untested-mode optgroups, the badge and the honest speed copy.
- The Lighting page layout and preview are the strongest screen in the app.
- Text contrast passes everywhere in both themes (table below).
